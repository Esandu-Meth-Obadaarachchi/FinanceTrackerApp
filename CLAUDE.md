# FinTrack — Claude guide

A Flutter app (web + Android) backed by Firebase (Auth + Firestore). The UI
is a faithful port of `Financial Tracker _Standalone_.html`. Use this file
as your map of conventions and gotchas before editing.

## Stack

- **Flutter** 3.32+ / Dart 3.8 — material widgets, no flutter_localizations.
- **Firebase** — `firebase_core`, `firebase_auth`, `cloud_firestore`.
- **Google Sign-In** — `google_sign_in` (mobile native picker, web popup).
- **State** — `provider` (ChangeNotifier). No Riverpod, no Bloc.
- **Fonts** — `google_fonts` (DM Sans for text, DM Mono for figures).
- **Local prefs** — `shared_preferences` (theme, reminder times, SMS toggle).
- **CSV export** — `share_plus` (web download + native share).
- **Local notifications** — `flutter_local_notifications` + `timezone` +
  `flutter_timezone` (daily + due-payment reminders; Android/iOS, no-op on web).
- **Push** — `firebase_messaging` (global `all`-topic broadcasts; Android/iOS).
- **SMS import** — `another_telephony` (Android-only bank-SMS auto-import).

`pubspec.yaml` is the source of truth — keep deps pinned with caret.

## Critical patterns

### Modals must re-expose AppState
`AppState` is provided in [main.dart `AuthGate`](lib/main.dart) — **below** the
root navigator. `showModalBottomSheet` and `showDialog` insert the route
**above** that provider, so a naive `context.read<AppState>()` inside a sheet
throws `ProviderNotFoundException` and the app crashes.

Every sheet entry point goes through `_showWithState(context, sheet)` in
[`screens/modals/sheets.dart`](lib/screens/modals/sheets.dart), which
re-wraps the builder in `ChangeNotifierProvider<AppState>.value`. Add new
sheets the same way. `ThemeController` is provided above MaterialApp so it
is reachable from sheets unchanged.

### Account balance is computed, never stored
`Account.openingBalance` is the only persisted figure. The current balance
is `AppState.balanceOf(account)` — opening + the effect of every relevant
transaction (income received +, expense -, transfer - source / + dest),
**minus any pending lent loan** drawn from that account. Don't add a mutable
`balance` field; add a transaction (or loan) and let the reducer math
reflect it.

### Lent money leaves the account, and comes back as income
Money math for loans lives in [`models/loan_math.dart`](lib/models/loan_math.dart)
as **pure functions** — deliberately free of Firestore so it can be unit
tested ([`test/loan_math_test.dart`](test/loan_math_test.dart)). `AppState`
only delegates. Put new balance rules there, with a test.

A `lent` loan is money that has physically left its `accountId`, so
`accountBalance()` subtracts it. The deduction is the **original
`loan.amount`** and holds for the **life of the loan** — it does *not*
shrink as repayments arrive. That is the one rule to get right here: each
repayment already returns as its own income transaction, so shrinking the
deduction too would credit the same money twice. Worked through:

```
lend 10,000        deduction -10,000                       → -10,000
repay 4,000        deduction -10,000, income +4,000        →  -6,000  (6k still out)
repay 6,000 more   deduction -10,000, income +10,000       →       0  (square)
```

Loans marked repaid *before* partial repayments existed have no offsetting
income transaction, so they deduct nothing and their balances are left
untouched — hence `loanDeductsFromBalance()` requires `isPending ||
hasPayments`. Borrowed loans are still **not** reflected in balances;
repaying one is simply an expense, which reduces the balance on its own.

**Settlement is derived, never stored.** A payment is a normal transaction
tagged with `loanId` (mirroring `recurringId`), and `loanRepaid()` sums
them. There is no `repaid` field to drift out of step, and deleting a
payment entry cleanly undoes it. For the same reason the UI asks
`AppState.isSettled(loan)` rather than reading `loan.status`: deleting
payments must reopen a loan rather than strand it as `repaid` with money
still outstanding. The stored `status` is a cache, only authoritative for
loans that have no payments at all.

`AppState.totalLent` / `totalBorrowed` sum **outstanding** on unsettled
loans; the dashboard surfaces lent alongside pending income in "To Receive".

### Pending income splits — it does *not* settle like a loan
Receiving part of a pending income (`AppState.receivePendingIncome()`, math in
[`models/income_math.dart`](lib/models/income_math.dart)) **splits** the entry:
a new `received` transaction for the money that arrived, and the pending one
shrunk by the same amount. Receiving the last of it just flips the original to
`received` rather than leaving a zero-value row behind.

This is deliberately the opposite of the loan rule above, and the asymmetry is
the thing to understand before touching either:

|  | loan | pending income |
|---|---|---|
| the record | a `loans` doc — principal never moves | *is* a transaction |
| its amount means | what was originally lent | what is **still owed** |
| settling | tag a payment with `loanId`, derive outstanding | shrink the entry, split off a receipt |

A loan has a principal worth preserving, so payments are tagged and outstanding
is derived. A pending income has no principal to preserve — its amount is the
outstanding figure — so shrinking it is the honest model. Tagging receipts onto
an untouched pending entry instead would put a 50,000 pending row *and* a
20,000 received row on screen for 50,000 of income, and every pending-income
total would have to subtract receipts to stay correct.

Because the pending amount stays equal to what is outstanding, `balanceOf()`
and every "pending income" sum keep working **untouched** — pending income is
already excluded from balances, and each receipt is an ordinary `received`
income. Receipts carry `parentId` for provenance only; nothing sums it.

### Recurring transactions are materialized client-side
A `recurring/{ruleId}` rule is a template; the actual entries are normal
`transactions` documents tagged with `recurringId`. `AppState._materializeRecurring()`
(no Cloud Functions — free tier) runs once accounts + transactions + recurring
streams are all ready and again whenever they change. For each `active` rule it
generates one transaction per month from `startMonth` (or the month after
`lastGeneratedMonth`) up to the current calendar month, then bumps
`lastGeneratedMonth`. That high-water mark is the idempotency key: it survives
across sessions/devices and means a **deleted** generated entry is **not**
recreated. A `_materializing` lock + in-session `_generated` set guard against
the re-entrancy caused by our own writes re-triggering the stream. Editing a
rule only affects future months; per-month edits are just edits to the
generated transaction. Reach the manager via `openRecurringManager(context)`
(re-provides `AppState`, like sheets do) from the Transactions screen.

### Per-user Firestore layout
Each user owns a `users/{uid}/{accounts,transactions,loans,recurring,budgets,reminders,chats}`
subtree; rules restrict access to the owner. Full field-by-field schema, ordering
and deploy command live in the **Database architecture** section below.

### Local notifications & reminders
[`NotificationService`](lib/services/notification_service.dart) is a singleton
initialised in `main.dart` (timezone via `flutter_timezone`, three Android
channels: `daily_reminders`, `due_reminders`, `general`). It is a **no-op on
web** and every call is failure-tolerant; exact-alarm scheduling falls back to
inexact. `HomeShell` requests permission once per signed-in session and re-arms
the daily reminders. Daily-reminder prefs (morning/night on + times) live in
SharedPreferences and are edited from Settings. Custom reminders are stored in
Firestore and turned into local notifications by
[`ReminderScheduler`](lib/services/reminder_scheduler.dart): ids are derived
deterministically from the reminder id, and `AppState` calls `syncAll()` on
every reminders snapshot (it also cancels reminders that disappeared). Local
schedules don't survive a reinstall, so they're re-derived from Firestore on
launch.

### FCM broadcasts (global, manual send)
[`MessagingService`](lib/services/messaging_service.dart) subscribes every device
to the `all` topic (and `user_{uid}` for future targeted sends), shows
foreground messages via the local-notifications plugin, and registers a
top-level background handler. **Android/iOS only** — the web client SDK can't
subscribe to topics. On the free tier there's no server: send a broadcast by
hand from **Firebase Console → Messaging → new notification → target topic
`all`**. The Android default channel is `general` (manifest meta-data).

### Bank SMS auto-import (Android only)
[`SmsParser`](lib/services/sms_parser.dart) is pure Dart (unit-testable): it
returns a result only when a message has an amount, a clear debit/credit
direction **and** a card/account tail — otherwise null, so OTP/balance noise is
ignored. [`SmsService`](lib/services/sms_service.dart) (opt-in, toggled in
Settings; needs `READ_SMS`/`RECEIVE_SMS`) listens live and scans the last 2 days
of inbox on start; it posts a transaction only when the tail maps to **exactly
one** account's `smsIds`, de-duping by body signature in SharedPreferences.
Everything is guarded behind `!kIsWeb && Android` so web/iOS still build. The
app-killed background case is intentionally not handled.

### Phone-frame layout on wide screens
`main.dart`'s `MaterialApp.builder` wraps every route in
`Center > ConstrainedBox(maxWidth: 480)` on a `Brand.backdrop` background.
Keep new top-level routes happy with that: don't assume full viewport width.

### Theme & colour helpers
Read colours with `context.watch<ThemeController>().colors` (a `Palette`).
Constants that don't change with theme (income green, expense red, gradients)
live on `Brand` in [palette.dart](lib/theme/palette.dart). Don't hardcode
hex inside screens unless it matches one of those.

### Google sign-in
[`AuthService.signInWithGoogle()`](lib/services/auth_service.dart) uses
`FirebaseAuth.signInWithPopup` on web (`kIsWeb`) and `google_sign_in`'s
native picker on mobile, then exchanges the Google credential with
FirebaseAuth. `signOut()` also calls `GoogleSignIn.signOut()` on mobile so
the next sign-in re-prompts for the account.

Android needs the debug/release keystore **SHA-1** registered on the
Firebase Android app, otherwise the Google picker fails with
`DEVELOPER_ERROR` / code 10. After adding a fingerprint, re-run
`flutterfire configure --project=fintrack-05220041 --platforms=android,web --yes`
to pull a fresh `google-services.json` (it'll contain an `oauth_client`
with `client_type: 1` once the SHA-1 is registered).

### Brand logo
The PNG at [`assets/logo.png`](assets/logo.png) is rendered via
`Image.asset` on the auth screen and also copied (manually) to
`web/favicon.png`, `web/icons/Icon-*.png`, and the
`android/app/src/main/res/mipmap-*/ic_launcher.png` set. When the logo
changes, update the source file and re-copy to those locations.

### Modern Color API
Flutter 3.27+ deprecated `Color.value` and `withOpacity`. Use:
- `color.toARGB32()` (see [utils/color_x.dart](lib/utils/color_x.dart))
- `color.withValues(alpha: 0.x)`

## Database architecture

Cloud Firestore (region `asia-south1`), one document tree per user. There is
no server backend — the Flutter client talks to Firestore directly and
`firestore.rules` is the only access boundary.

### Collection tree
```
users/{uid}                       — implicit parent; no fields of its own
  ├─ accounts/{accountId}
  ├─ transactions/{txId}
  ├─ loans/{loanId}
  ├─ recurring/{ruleId}
  ├─ budgets/current              — the single per-user zero-based plan
  ├─ reminders/{reminderId}
  ├─ settings/notes               — the user's quick notes
  └─ chats/{chatId}               — saved assistant conversations, max 5
```
`uid` is the FirebaseAuth user id. All collections are read live as streams in
[`firestore_service.dart`](lib/services/firestore_service.dart) and held in
[`AppState`](lib/state/app_state.dart). Most documents are written with a
`createdAt` server timestamp (`FieldValue.serverTimestamp()`) on create; it is
not part of the model `toMap()` and `update*` calls don't touch it. (Budgets
are an upsert keyed by month, so their `createdAt` is rewritten on each save and
behaves as last-updated.)

### Documents

**accounts/{accountId}** — a money account ([account.dart](lib/models/account.dart))

| field | type | notes |
|---|---|---|
| `name` | string | display name |
| `type` | string | `bank` \| `cash` \| `fd` (fixed deposit) |
| `colorHex` | string | `#RRGGBB`, default `#3DEBA8` |
| `openingBalance` | number | the **only** persisted balance figure; live balance is computed (see "Account balance is computed") |
| `smsIds` | array<string> | card/account number tails (e.g. `"6709"`) used to match bank SMS for auto-import; empty disables it |
| `createdAt` | timestamp | server-set; stream ordered by this ascending |

**transactions/{txId}** — income / expense / transfer ([app_transaction.dart](lib/models/app_transaction.dart))

| field | type | notes |
|---|---|---|
| `date` | string | `YYYY-MM-DD` (no time component) |
| `type` | string | `income` \| `expense` \| `transfer` |
| `accountId` | string | source account (the account for income/expense) |
| `toAccountId` | string\|null | transfer destination; null otherwise |
| `category` | string | from [data/categories.dart](lib/data/categories.dart) |
| `note` | string | free text |
| `amount` | number | always positive; sign is derived from `type` |
| `status` | string | `received` \| `pending` (meaningful for income; else `received`) |
| `recurringId` | string\|null | set when auto-generated by a recurring rule (else null) |
| `loanId` | string\|null | set when this entry settles part of a loan (else null) |
| `parentId` | string\|null | set when this entry was split off a part-paid pending income (provenance only — nothing sums it) |
| `createdAt` | timestamp | server-set; stream ordered by `date` descending |

**loans/{loanId}** — money lent or borrowed ([loan.dart](lib/models/loan.dart))

| field | type | notes |
|---|---|---|
| `loanType` | string | `lent` \| `borrowed` |
| `who` | string | counterparty name |
| `amount` | number | positive |
| `reason` | string | free text |
| `date` | string | `YYYY-MM-DD` |
| `accountId` | string | account the money moved through |
| `status` | string | `pending` \| `repaid` — a cache; see below |
| `createdAt` | timestamp | server-set; stream ordered by this descending |

There is **no `repaid` amount field**. How much of a loan is settled is the
sum of the `transactions` tagged with its `loanId`, so the two can never
drift apart (see "Lent money leaves the account"). `status` is written to
`repaid` by `recordLoanPayment()` when the last of the balance is cleared,
but it is only authoritative for loans with no payment transactions at all
— everywhere else the UI asks `AppState.isSettled()`.

Settling a loan creates a real transaction: `income` / `Loan Received` for a
lent loan, `expense` / `Loan Repayment` for a borrowed one.

**recurring/{ruleId}** — fixed monthly income/expense automation ([recurring_rule.dart](lib/models/recurring_rule.dart))

| field | type | notes |
|---|---|---|
| `type` | string | `income` \| `expense` (no transfer) |
| `accountId` | string | account entries are posted to |
| `category` | string | from [data/categories.dart](lib/data/categories.dart) |
| `note` | string | free text |
| `amount` | number | per-month amount |
| `dayOfMonth` | number | 1–31, clamped to month length when generating |
| `status` | string | income only: `received` \| `pending` |
| `active` | bool | paused rules generate nothing |
| `startMonth` | string | `YYYY-MM`, first month to generate |
| `lastGeneratedMonth` | string\|null | high-water mark; null until first run |
| `createdAt` | timestamp | server-set; stream ordered by this descending |

See "Recurring transactions are materialized client-side" below.

**budgets/current** — the one zero-based / envelope plan per user ([budget_plan.dart](lib/models/budget_plan.dart))

There is a **single** budget doc per user, always at id `current` (not one per
month). Its `month` field records which month the plan currently belongs to.

| field | type | notes |
|---|---|---|
| `month` | string | `YYYY-MM` the plan belongs to (a **field**, not the doc id) |
| `plannedIncome` | number | expected income for the month |
| `allocations` | map<string,number> | category label -> planned total |
| `items` | map<string, array<{name,amount}>> | optional line-item breakdown per category; when present, `allocations[cat]` == sum of its items |
| `createdAt` | timestamp | server-set; full overwrite on each save so doubles as last-updated |

Saved with a full `set` (no merge) so removed allocations/items are actually
dropped. Actual spend per category is derived from `transactions` in
`plan.month` (not stored). The zero-based goal is
`plannedIncome - sum(allocations) == 0`. **Carry-over**: when `plan.month`
differs from the current month, the planner shows a banner to bring the plan
into the new month (updates `month`, keeps allocations) or start fresh.

**reminders/{reminderId}** — custom due-payment reminder ([reminder.dart](lib/models/reminder.dart))

| field | type | notes |
|---|---|---|
| `title` | string | the reason, e.g. "Credit card minimum payment" |
| `amount` | number | optional; 0 = none |
| `dueDate` | string | `YYYY-MM-DD` |
| `times` | number | how many reminders (>= 1) |
| `intervalDays` | number | gap between reminders in days (>= 1) |
| `time` | string | `HH:mm` time of day to fire |
| `active` | bool | paused reminders schedule nothing |
| `createdAt` | timestamp | server-set; stream ordered by `dueDate` ascending |

**settings/notes** — the user's quick notes ([note_presets.dart](lib/models/note_presets.dart))

| field | type | notes |
|---|---|---|
| `income` | array<string> | headings offered when adding an income, e.g. `"Tehan class"` |
| `expense` | array<string> | headings offered when adding an expense |

A single document, fully overwritten on each change. Capped at 30 per type, no
case-insensitive duplicates. They are managed in **Settings → Quick notes**.
In the add/edit transaction sheet they appear as an optional dropdown: picking
one becomes the entry's `note` and hides the text field; leaving it empty keeps
the free-text field working as before. The stored `note` is just the string, so
there is no link back to the preset: renaming or deleting one never changes past
entries, and an edited entry whose note equals a preset reopens with it selected.
The assistant gets them in its snapshot (`notePresets`) and matches against them.

**chats/{chatId}** — a saved assistant conversation ([chat_session.dart](lib/models/chat_session.dart))

| field | type | notes |
|---|---|---|
| `title` | string | the opening question, shortened to 40 chars |
| `messages` | array<map> | `{role, text, tools, provider, question?, proposal?}`; capped at the newest 100 |
| `state` | map | the agent's echoed clarification state, restored so a half-finished question resumes |
| `applied` | array<string> | proposal ids already applied, so a reopened card never offers a second Apply |
| `dismissed` | array<string> | proposal ids the user cancelled |
| `updatedAt` | timestamp | server-set on every save; the stream orders by it, descending |

A user holds at most **5** (`kMaxChats`). `FirestoreService.createChat()` reads
the collection fresh and deletes the least recently *updated* ones in the same
batch as the new document, so the cap holds even before the live stream has
loaded. It evicts by last-updated, not created: a chat still in use should
never be the one that ages out (`chatIdsToEvict`, unit-tested). The chat doc is
only created on the first message, so an empty chat is never stored; later saves
are whole-document `set`s through `updateChat()`.

Reminders are materialised into **local** notifications by
[`reminder_scheduler.dart`](lib/services/reminder_scheduler.dart) (see
"Local notifications & reminders"). No server send.

### Security rules
[`firestore.rules`](firestore.rules) (rules v2) grants read/write on the whole
`users/{userId}/**` subtree only when `request.auth.uid == userId`. A user can
never see another user's tree. Deploy with:
```
firebase deploy --only firestore:rules --project=fintrack-05220041
```

### Indexes
[`firestore.indexes.json`](firestore.indexes.json) is empty — every stream
sorts on a single field (`createdAt`, `date` or `dueDate`), reads a single doc
(`budgets/current`), so only Firestore's automatic single-field indexes are
needed. Adding a query that filters + orders on different fields will require a
composite index here.

### Reset all data
[`FirestoreService.resetAllData()`](lib/services/firestore_service.dart) deletes
every document across `accounts`, `transactions`, `loans`, `recurring`,
`budgets`, `reminders`, `settings` (quick notes) and `chats` (batched in chunks of 400). There is **no undo**. It
is reached from **Settings → Danger Zone → Reset all data** behind a
confirmation dialog. After the wipe the live streams emit empty, which also
cancels any scheduled reminder notifications via `ReminderScheduler.syncAll`.
Local prefs (theme, daily-reminder times, SMS dedupe set) are **not** touched.

## AI features and the `backend/` service

Three features share one FastAPI service in [`backend/`](backend/README.md):
the bank-SMS review inbox, the local category memory, and the assistant. It
exists because a Flutter web bundle is fully inspectable and so cannot hold
an API key.

> **Full documentation:** [`backend/README.md`](backend/README.md) covers
> running the service, every endpoint with worked examples, configuration and
> troubleshooting. [`backend/docs/AI.md`](backend/docs/AI.md) covers the AI
> design — the layering, the provider fallback, the RAG and agent loop, and
> why there is no vector store. The summary below is the short version.

**Providers.** `claude-haiku-4-5` handles every request, with
`gemini-3.6-flash` as the free fallback (`PRIMARY_PROVIDER` flips it).
Claude leads on measured latency: **2.7s median against Gemini's 34.5s**,
because Flash 3.x thinks on every turn and thrashes on tool use, burning all
three iterations where Claude answers in two. The fallback fires on **any**
primary failure, including a 400 — the two vendors validate differently (Gemini 3.x
rejects tool histories missing a `thoughtSignature`, which Claude has no
concept of), so "4xx means the next provider will fail too" is wrong here.
`response.provider` says who answered.

Two Gemini quirks are handled in `providers/gemini.py` and worth knowing
before touching it: Flash 3.x **always** thinks (`thinkingBudget: 0` is
rejected) and those tokens come out of `maxOutputTokens`, so a tight budget
returns `MAX_TOKENS` with empty content; and its function calls carry a
`thoughtSignature` that must be echoed back or the next turn 400s.

### Everything is layered cheapest-first

The ordering is the design, not an optimisation:

1. **Local memory** ([`models/category_memory.dart`](lib/models/category_memory.dart))
   — instant, free, offline, and correct for anything seen before.
2. **Regex** ([`services/sms_parser.dart`](lib/services/sms_parser.dart)) —
   amount and direction out of a bank SMS.
3. **The model** — only for text nothing local recognises.

`CategoryMemory` refuses to answer when its top two categories are close.
A confident wrong suggestion is worse than silence: the user stops trusting
the fill-in and checks every field by hand, which is the friction the
feature exists to remove.

### The review inbox replaced auto-import

`SmsService` no longer writes transactions. It feeds
[`SmsInbox`](lib/services/sms_inbox.dart), which queues suggestions the user
approves.

The old guard posted only when regex matched **and** the tail mapped to
exactly one account, and dropped everything else silently. That one rule was
doing two jobs — keeping bad data out, and choosing what to show — and did
the second badly. Because nothing is written without a tap now, the bar for
showing something is only "probably useful". Approving teaches the memory,
so the same merchant costs nothing next time.

Suggestions live in SharedPreferences, not Firestore: a queue of unreviewed
guesses is per-device working state. The approved transaction is the only
thing worth syncing.

### The assistant is agentic, and stateless server-side

The client posts a snapshot of its own data with each question
(`AiService.buildSnapshot`), with balances and loan outstandings already
computed so the model never re-derives money rules the app owns. Tools in
`backend/app/services/tools.py` filter and aggregate that snapshot, so the
backend needs **no Firestore credentials** and retains nothing.

Tools are pure functions of `(snapshot, arguments)`, which is what makes
them testable without a model or a network. Ids travel in the snapshot so
the agent can act on a specific row rather than describing one.

### A turn ends in one of three ways

`/agent/ask` replies with a `kind`, and the client renders each differently:

| `kind` | Means | Client shows |
|---|---|---|
| `answer` | It answered | A chat bubble |
| `question` | It needs something first | The text plus tappable option chips |
| `proposal` | It wants to write | A confirmation card, nothing saved yet |

**Only reading spends the iteration budget.** `MAX_ITERATIONS` is 3, which
sounds tight and is not: `ask_user` and the `propose_*` tools in
[`actions.py`](backend/app/services/actions.py) are **terminal** and stop the
loop the moment they are called, so a write or a clarification costs one
model call rather than eating the budget.

### The agent cannot write, by construction

The backend has no database credentials, so a `propose_*` tool validates a
draft and hands it back. The client applies it through `AppState` on Apply.
That makes "confirm before saving" **structural rather than a policy** — there
is no path where an AI write reaches Firestore without a tap, and because it
goes through the same `AppState` methods as a hand-typed entry, every money
rule above still holds. The agent gets no privileged route around them.

Add, edit and delete are all supported. Edit and delete carry `before` so the
card shows what is being replaced or removed — the risk with those is not the
write but approving one without seeing what it overwrites. Deleting an entry
tagged `loanId` or `parentId` warns that it unwinds a derived rule.

A rejected draft goes back to the model as a **tool result it can correct**,
not an error the user sees. The exception is a draft that only lacks a usable
account (none named, or one that does not exist): `run_agent` answers that
itself with an `ask_user`-style question whose options are the real account
names, and keeps the draft in `state` so the next tap resumes it. Left to the
model, repeated rejections ate the iteration budget and the turn ended as
prose with no chips and no Apply card. The no-tools fallback is also told it
cannot propose anything, so it never points at an Apply button that is not there. One rejection worth knowing: a negative amount is
refused rather than `abs()`-ed, because direction lives in `type` and
flipping the sign silently would turn `income -1200` into income of **+1200**.

### Notes: snap to a saved one, ask with buttons, never loop

For a new entry the agent only passes `note` when the user said what it was for.
`match_note()` ([actions.py](backend/app/services/actions.py)) snaps it to the
closest saved note, but only when it is clearly the same thing: exact, one
containing the other, or a close typo. A weak match or a **tie** between two
presets keeps the user's own words rather than guessing. If no note was given and
notes are saved, `run_agent` asks "What's this for?" itself, with the saved notes
plus a **No note** chip, so it costs no model call. Once the user has answered
(`pending.field == "note"`) the question is never asked again, whatever the model
passes, so a forgetful model cannot loop. With no saved notes the note falls back
to the category, as before.

The prompt also forbids questions that expect a typed "yes": the proposal card
already has Add and Cancel, and any choice goes through `ask_user` as buttons.

### Clarifications need explicit state, not just history

`ask_user` only fires when the model can offer 2–4 tappable options — asking
is acceptable when it costs one tap, not typing. Two cases are forced: a
total with no time period ("what is my income?"), and which account when the
user holds several.

The reply carries a `state` object the client **echoes back untouched**. Chat
history alone would leave the model re-inferring its own half-finished intent
from prose, which is where these loops break. The backend stays stateless —
the device is the memory.

### Rules that matter here

- **Nothing AI-generated is ever saved without confirmation.** Parsing
  returns drafts and the agent returns proposals. One wrong silent write
  costs more trust than a hundred right ones earn.
- **Proposals carry an `id`.** Track applied ones so a double tap cannot
  write twice, and keep cancelled apart from applied or a dismissed card
  claims it saved something.
- **`confidence` below 0.6** means the model guessed: open the sheet rather
  than offering one-tap approve.
- **AI is off by default**, configured in Settings. Without a reachable
  backend every AI path would sit on a timeout.
- **Secrets live in `backend/.env`**, which is gitignored. Set
  `APP_SHARED_KEY` before hosting or the endpoint is an open proxy onto paid
  credits.

## Git workflow

- **Never commit straight to `main`.** Every new feature or fix starts on its
  own branch off `main` — `feature/<short-name>` for new work,
  `fix/<short-name>` for bug fixes, `docs/<short-name>` for documentation.
- **Commit at the end of each subtask**, not once at the end of the whole job.
  A branch should read as a sequence of self-contained steps.
- Write a proper commit message: a short imperative subject line (`Add
  responsive desktop layout`, not `changes` or `wip`), and a body explaining
  *why* whenever the reason isn't obvious from the diff.
- **Do not add `Co-Authored-By: Claude` or any other AI attribution trailer**
  to commit messages.
- Run `flutter analyze` before each commit and keep it clean.

## House rules

- Don't reach for `intl` — the formatters in [utils/formatters.dart](lib/utils/formatters.dart) cover everything.
- Don't introduce a new state-management library. `provider` is enough.
- New persisted fields go on the model + `toMap`/`fromMap`. No JSON codegen.
- Keep `flutter analyze` clean before committing.
- LKR is the only currency; show as `Rs 12,345` via `fmt()` or `fmtFull()`.
- Use `MaterialPageRoute` / `showAppSheet` for new screens/sheets — never push raw widgets that read `AppState` onto the root navigator without re-providing it.
